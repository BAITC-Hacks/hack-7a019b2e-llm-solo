# Инструкция бэкендеру — «Граф денег»

## 1. Задача простыми словами

Бэкенд должен дать интерфейсу данные для сценария: список приоритетных клиентов → карточка клиента → его связи и переводы → объяснение роли. Результаты помогают выбрать порядок проверки, а не устанавливают виновность.

Предлагаемое разделение: Python рассчитывает роли, кластеры и приоритет; Go загружает результаты, связывает их с исходными данными и отдаёт API. Аналитические формулы не дублируем в Go.

Этот документ содержит проверенные факты о данных и предлагаемый контракт для реализации. API ниже пока не реализован. В текущем проекте работает Python-пайплайн и генерация HTML, отдельного Go-сервера нет.

## 2. Что лежит в data/

Parquet — исходные таблицы организаторов. CSV с теми же именами — подготовленные нами копии для просмотра и возможного импорта. Не загружать оба формата одновременно как разные данные. Источник истины — Parquet; при использовании CSV проверять их соответствие исходникам.

### nodes.parquet — клиенты, 2 248 строк

| Поле | Исходный тип | Значение |
| --- | --- | --- |
| gid | int64 | Обезличенный ID клиента, уникальный ключ |
| depth | int64 | Уровень обхода 0–4, не ранг в иерархии группы |
| is_seed | bool | Исходный клиент, от которого начали обход |

Seed-клиентов 81. Распределение по depth: 0 → 81, 1 → 472, 2 → 462, 3 → 789, 4 → 444. Есть 19 клиентов без рёбер: их нельзя терять при построении графа или поиске.

### edges.parquet — агрегированные связи, 3 119 строк

| Поле | Исходный тип | Значение |
| --- | --- | --- |
| src | int64 | ID отправителя, ссылка на nodes.gid |
| dst | int64 | ID получателя, ссылка на nodes.gid |
| sum_kzt | float64 | Сумма переводов от src к dst за период |
| n_tx | int64 | Количество переводов этой пары |
| depth | int8 | Уровень обхода связи |

Ключ связи — направленная пара (src, dst). A → B и B → A — разные связи. В текущем наборе пары уникальны, переводов самому себе нет.

### transactions.parquet — отдельные переводы, 4 840 строк

| Поле | Исходный тип | Значение |
| --- | --- | --- |
| src | int64 | Отправитель |
| dst | int64 | Получатель |
| date | datetime64[ns] | Дата операции; фактической точности до времени суток нет |
| sum_kzt | float64 | Сумма конкретного перевода |

Период: 2026-07-01 — 2026-07-31. Минимальная наблюдаемая сумма: 5 000 ₸. Суммарный оборот: 365 890 012,01 ₸.

**Не удалять одинаковые транзакции:** обнаружены 97 повторов сверх первых совпадений по всем четырём полям. В исходнике нет transaction_id; совпадение полей не доказывает ошибочное дублирование. При необходимости внутреннего ключа используйте номер исходной строки в пределах конкретной версии набора; не называйте его банковским ID.

## 3. Как таблицы связаны

```text
nodes.gid ← edges.src / edges.dst
nodes.gid ← transactions.src / transactions.dst

transactions GROUP BY src, dst:
    SUM(sum_kzt) = edges.sum_kzt
    COUNT(*)    = edges.n_tx
```

Условный пример: три перевода A → B на 10, 20 и 30 тысяч дают одну связь A → B на 60 тысяч с n_tx=3. Это два представления одних операций: не складывать обороты edges и transactions между собой.

При проверке текущих Parquet: пропусков нет; gid уникальны; пары и количества согласованы; максимальное отличие агрегированных сумм ≈ 5,82×10⁻¹¹ ₸ из-за float. При сверке денег использовать документированный допуск, например 0,01 ₸, а не точное равенство float.

## 4. Что важно при реализации на Go

- Читать ID как int64 или строки без промежуточного float. Во всех JSON-полях gid/src/dst и списках ID использовать строки: числа больше безопасного диапазона JavaScript.
- Для CSV применять CSV-парсер, а не strings.Split: в выходных файлах встречаются кавычки и запятые внутри полей. Наши CSV записаны в UTF-8 с BOM; убрать BOM из первого заголовка при импорте.
- Даты отдавать как YYYY-MM-DD. Не выводить фиктивное время 00:00 как точное время банковской операции и не менять день через часовой пояс.
- Не округлять деньги до целых тенге при хранении или API. Для точной арифметики можно использовать целые тиыны после проверки точности исходных значений; формат конвертации должен быть общим с Python.
- Загрузить данные один раз при старте. Создать индексы по gid, входящим/исходящим связям и транзакциям клиента. База данных для этого объёма не обязательна.
- Сначала создать клиентов из nodes, затем связи. Так сохранятся изолированные клиенты.
- Ошибки загрузки, отсутствующие результаты и неизвестные роли не заменять молча пустыми данными или нулями.

## 5. Где брать результаты Python

Из корня после установки зависимостей:

```powershell
.\.venv\Scripts\python.exe starter/starter.py --data data --out out
```

| Файл | Поля |
| --- | --- |
| out/nodes_roles.csv | gid, role, role_score, cluster_id, priority_score, evidence |
| out/clusters.csv | cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis |
| out/top_nodes.csv | rank, gid, role, priority_score, why |

Допустимые роли: consolidator, transit, distributor, terminal, coordinator, peripheral. Оценки лежат в [0,1], но не являются вероятностями виновности. Полный список клиентов брать из nodes_roles, а не top_nodes: топ содержит только часть сети.

Текущая реализация сохраняет числовые метрики преимущественно внутри создаваемой HTML-страницы. **Не извлекать данные парсингом HTML.** Для первой версии Go может читать исходные таблицы/CSV и три аналитических CSV; базовые суммы и количества получать из edges. Если нужен вклад PageRank/HITS и других признаков в объяснение, Python-разработчик должен добавить отдельный структурированный экспорт этих метрик.

Не менять обязательные CSV ради фронтенда. Дополнительный JSON допустим как отдельный контракт. Исправление передачи ID строками в существующем HTML ещё нужно проверить/выполнить.

## 6. Предлагаемый API для MVP

| Метод и путь | Результат |
| --- | --- |
| GET /api/health | Готовность данных и аналитических результатов |
| GET /api/summary | Число клиентов/связей/переводов/seed, период, оборот |
| GET /api/top?limit=20 | Первые клиенты рейтинга, их роль, приоритет, why |
| GET /api/nodes/{gid} | Поля клиента, роль, кластер, оценки, evidence и агрегаты входа/выхода |
| GET /api/nodes/{gid}/neighbors?direction=both&hops=1 | Подграф вокруг клиента с направленными рёбрами |
| GET /api/nodes/{gid}/transactions?offset=0&limit=100 | Переводы клиента с датами и суммами |
| GET /api/clusters | Список групп и их характеристики |
| GET /api/clusters/{cluster_id} | Участники и внутренние связи выбранной группы |

Договорённости для фронтенда:

- Коллекции возвращать как `{ "items": [...], "total": 123 }`; total — число совпадений до ограничения страницы. Подграф — `{ "nodes": [...], "edges": [...], "truncated": false }`.
- В карточке использовать точные имена gid, depth, is_seed, role, role_score, cluster_id, priority_score, evidence, in_deg, out_deg, in_kzt, out_kzt, in_tx, out_tx.
- В JSON рёбер сохранить src, dst, sum_kzt, n_tx, depth. У каждого ребра оба конца присутствуют в возвращаемом подграфе.
- direction: in, out или both. hops ограничить 1–2 в MVP. Даже при обходе both стрелки сохраняют исходное направление переводов.
- Для соседей ограничить ответ, например 500 узлами; при обрезке вернуть truncated=true. Это ограничение ответа API, не то же самое, что граница depth=4 исходной выборки.
- Пагинация транзакций: limit 1–500, offset ≥0; порядок date и номер исходной строки. Сохранить одинаковые операции. Для top ограничить limit 1–50, пока экспорт содержит 50 строк; при необходимости большего списка изменить контракт явно.
- Пустой список связей существующего клиента — 200, неизвестный gid — 404, некорректные параметры — 400, неготовые данные — 503. Ошибки: `{ "error": { "code": "node_not_found", "message": "Клиент не найден" } }`.
- Если выдаются даты/суммы по фильтру, аналитические оценки остаются рассчитанными на полном периоде. Не выдавать их за пересчёт на выбранный фильтр.

## 7. Что нельзя заключать из данных

- depth=4 без исходящих — возможно, оборванная цепочка, а не конечный получатель.
- Seed означает начало обхода. Его входящие потоки могут быть неполными.
- Структурная связь с несколькими seed не доказывает руководство группой.
- Роль и кластер — разные поля: роль описывает поведение, кластер — связанную группу.
- Нет персональных данных, назначения платежей и правильных меток ролей. Не придумывать ФИО, компании или точность модели.

## 8. Порядок работы бэкендера

1. Согласовать JSON-поля с фронтендом и Python-разработчиками; ID везде строковые.
2. Реализовать импорт и проверки, затем индексы в памяти.
3. Сделать health, summary, top и карточку клиента — первый сквозной сценарий.
4. Добавить соседей, транзакции и группы.
5. Подключить локальный интерфейс, обеспечить работу без внешних API/CDN.
6. Документировать запуск Go и общий запуск Python → Go. До появления Go-команды не объявлять её существующей. Аналитику не запускать заново на каждый GET-запрос.

## 9. Минимальная приёмка

- В текущем наборе загружены 2 248 клиентов, 3 119 связей и 4 840 операций; все 19 изолированных клиентов доступны по ID.
- Длинный gid проходит загрузку → JSON → поиск без изменения цифр.
- Повторяющиеся транзакции сохранены, n_tx и суммы совпадают с edges.
- Роли и рейтинги API совпадают с аналитическими CSV; evidence не потерян.
- Запрос неизвестного клиента, пустые связи и ошибочные параметры обрабатываются явно.
- По одному выбранному клиенту числа в карточке вручную сверены с исходными переводами.
- Локальный сценарий работает без сети. Исходные Parquet не изменяются, данные и результаты одной версии не смешиваются с другой.
