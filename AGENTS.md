# AGENTS.md — Граф денег

## Назначение и область действия

Инструкции для разработчиков и AI-агентов во всём проекте. Общайтесь с командой на русском. Имена полей, ролей и программных интерфейсов сохраняйте в согласованном формате.

Проект — локальный инструмент AML-аналитика для кейса Freedom: восстановить наблюдаемую финансовую структуру по переводам, предложить роли клиентов, выделить группы и объяснить порядок ручной проверки. Результаты — аналитические гипотезы, а не доказательства преступления или виновности.

## Обязательный результат

После установки зависимостей одна команда из корня должна сформировать результаты менее чем за пять минут на обычном ноутбуке:

```powershell
python starter/starter.py --data data --out out
```

Контракты CSV:

| Файл | Обязательные поля |
| --- | --- |
| `out/nodes_roles.csv` | `gid,role,role_score,cluster_id,priority_score,evidence` |
| `out/clusters.csv` | `cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis` |
| `out/top_nodes.csv` | `rank,gid,role,priority_score,why` |

- Каждый входной узел представлен ровно один раз в `nodes_roles.csv` и имеет кластер, включая изолированные узлы.
- `role_score` и `priority_score` — конечные числа в диапазоне [0, 1].
- Допустимые роли: `consolidator`, `transit`, `distributor`, `terminal`, `coordinator`, `peripheral`.
- `evidence` — не более 200 символов, содержит понятные числовые основания.
- В рейтинге не менее 20 уникальных клиентов на выданном наборе; сортировка по убыванию приоритета и воспроизводимое разрешение равенств.
- Интерфейс показывает направленные связи, окраску по ролям/кластерам, поиск по `gid` и объяснение выбранного клиента.
- Сдача включает код, README с самостоятельным запуском, три CSV, схему архитектуры и пятиминутное демо на 2–3 клиентах.
- Правила и пороги документированы: команда должна объяснить роли трёх произвольных клиентов примерно за минуту.
- Масштабирование до миллиона узлов объясняется в документации; реализация такого масштаба не является обязательной частью MVP.

## Данные и ограничения выводов

Исходники: `data/nodes.parquet`, `data/edges.parquet`, `data/transactions.parquet`.

| Набор | Поля |
| --- | --- |
| nodes | `gid`, `depth`, `is_seed` |
| edges | `src`, `dst`, `sum_kzt`, `n_tx`, `depth` |
| transactions | `src`, `dst`, `date`, `sum_kzt` |

Ориентиры для выданного набора: 2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81 seed. Это контрольные значения конкретного набора, а не константы алгоритма.

- Сохраняйте исходные архивы и Parquet без изменений. Не добавляйте придуманные транзакции, атрибуты клиентов или внешнее обогащение.
- Обход ограничен четырьмя переходами по исходящим переводам; суммы ниже 5 000 ₸ отсутствуют. Видимая сеть неполна.
- Узел `depth=4` без исходящих рёбер нельзя объявлять конечным получателем только из-за отсутствия этих рёбер.
- У seed входящие потоки могут быть неполными. Отношение исходящего оборота к входящему не является банковским балансом.
- Дата без времени не задаёт порядок операций внутри дня. FIFO и сопоставление потоков по дням — допущения, которые нужно раскрывать.
- Достижимость от seed не доказывает прохождение конкретных денег по пути и не устанавливает руководство группой.
- Ground truth ролей отсутствует. Не заявляйте accuracy, precision или вероятность виновности без соответствующей разметки и оценки.
- Не подгоняйте число кластеров под ориентиры организаторов. Кластер — структурная гипотеза, не доказанная организованная группа.
- Сохраняйте `gid`, `src`, `dst` без потерь: целые int64 либо точные строки в Python; строки на границе JSON/JavaScript. Не пропускайте идентификаторы через float или JavaScript Number.

## Аналитические правила

- Разделяйте вычисление признаков, назначение ролей, рейтинг, кластеризацию и экспорт.
- Храните пороги и веса явно; описывайте порядок правил, разрешение конфликтующих ролей и смысл оценок в README.
- Объяснение должно соответствовать фактически сработавшему правилу. Для приоритета показывайте существенные признаки, повлиявшие на рейтинг.
- Не называйте эвристическую оценку калиброванной вероятностью.
- Для случайных алгоритмов фиксируйте seed; для экспорта задавайте стабильный порядок строк.
- Направление сохраняйте в графе и анализе потоков. Неориентированную проекцию для кластеризации объясняйте отдельно.
- Не считайте оборот дважды: `edges` уже агрегирует транзакции. Внутренний оборот кластера — сумма направленных рёбер, оба конца которых внутри кластера.
- Не зашивайте ответы для конкретных `gid`. Конкретные клиенты допустимы в демонстрационных примерах и проверках.
- Не вводите тяжёлые графовые вычисления без оценки времени на полном наборе.

## Текущая структура и запуск

```text
data/                       исходные Parquet
starter/starter.py          текущий аналитический пайплайн
starter/viewer.html         шаблон интерфейса
starter/requirements.txt    зависимости
out/                        генерируемые CSV и HTML
architecture.svg            схема архитектуры в корне
README.md                   инструкции и методика
```

Текущая реализация — прототип, а не эталон правильной аналитики. Не считайте наличие файлов в `out/` доказательством успешного запуска текущей версии.

Устанавливайте зависимости в отдельное виртуальное окружение:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r starter/requirements.txt
.\.venv\Scripts\python.exe starter/starter.py --data data --out out
```

Используйте согласованную командой версию Python и проверенные версии библиотек. Все необходимые зависимости должны быть объявлены. Не полагайтесь на встроенный Python AI-агента или случайно установленный Parquet-движок. Не меняйте стек без практической необходимости.

Обязательный сценарий должен работать локально без внешних API и CDN. Runtime-LLM, GPU, Neo4j, Docker и платные сервисы не обязательны. AI-агент для разработки не означает обязательного AI-чата в продукте.

Генерируемые CSV и HTML исправляйте через код или шаблон, затем пересоздавайте. При рефакторинге сохраняйте команду запуска либо одновременно обновляйте README и проверяйте новый сценарий.

## Распределение команды из трёх человек

| Участник | Ответственность |
| --- | --- |
| Python №1 | Признаки, роли, рейтинг, числовые объяснения; логика `nodes_roles.csv` и `top_nodes.csv` |
| Python №2 | Загрузка и валидация, граф, кластеры, `clusters.csv`, общий запуск, экспорт и зависимости |
| Участник №3 | Интерфейс, поиск, карточка доказательств, интеграция демо, координация README и Git |

- Каждый пишет свой код, коммиты и документацию своей части. Интегратор не является единственным пользователем Git.
- До параллельных изменений согласуйте контракт данных и владельцев файлов. Не редактируйте одновременно одни участки монолитного `starter.py`.
- При необходимости выделите модули `features`, `roles`, `ranking`, `graph`, `clusters`, `pipeline`; это предлагаемая структура, сейчас таких файлов может не быть.
- Интерфейс сначала может использовать явно обозначенный пример согласованного формата; к сдаче подключаются реальные результаты.
- Зависимости и точку входа координирует Python №2. Основная ветка должна оставаться запускаемой.
- Работа команды из трёх человек сама по себе не поручает AI-агенту создавать субагентов. Делегирование агентам выполняйте по явному запросу пользователя.

## Проверки перед готовностью

Выполняйте проверки, соответствующие изменениям. Для правок только документации достаточно сверить команды, пути и утверждения; не добавляйте бессодержательные тесты.

Для изменений аналитики и перед сдачей:

1. Проверить схемы входных файлов, уникальность узлов, ссылки рёбер на существующие узлы и согласованность агрегатов с транзакциями. Объяснить допустимую погрешность денежных сумм.
2. Запустить пайплайн; записать время и фактический результат. Не выдавать старый замер за новый.
3. Сверить множество выходных `gid` со входом, отсутствие дубликатов/пустых обязательных полей, словарь ролей, диапазоны оценок и длину `evidence`.
4. Проверить принадлежность каждого узла ровно одному кластеру, размеры, число seed и внутренние обороты кластеров.
5. Проверить уникальность и порядок топ-листа, соответствие ролей и приоритетов основной таблице.
6. Проверить изолированный узел, границу depth=4, неполные потоки seed, деление на ноль и точность идентификаторов. Использовать небольшие искусственные графы для проверки правил отдельно от исходного набора.
7. В браузере проверить точный поиск длинного `gid`, выбор узла, направления, фильтры и соответствие карточки CSV. Проверить работу без сети.
8. Повторить запуск по README в чистом окружении; убедиться, что схема архитектуры находится по указанному пути и отражает реализацию.

Критерий готовности: рабочая цепочка «данные → расчёты → CSV → интерфейс», объяснимые результаты и воспроизводимый запуск. Не заявляйте готовность только по успешному завершению скрипта.
