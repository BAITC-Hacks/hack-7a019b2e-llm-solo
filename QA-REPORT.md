## Б2. Данные кейса нечем открыть

Датасет в формате parquet (`data/edges.parquet`, `data/nodes.parquet`,

Без решения по этому пункту данные кейса физически не открыть. Варианты:

1. **Остаться на Node, добавить `hyparquet`.** Ноль транзитивных зависимостей — минимальное
   нарушение принципа «без сторонних зависимостей» из `AGENTS.md`, и обоснование очевидное:

2. **Разовая конвертация parquet → NDJSON** скриптом на Python с `pyarrow`, дальше Node читает

3. **Перенести решение на Python** с `pandas` + `pyarrow`. Для графовой аналитики это

Объём данных снимает вопрос производительности: 4840 транзакций помещаются в память целиком,

## Блок A. Критично

### A1. Параллельная запись памяти теряет данные и сообщает об успехе

**Файл:** `src/memory.js:46-63` (`append`)
**Тест:** `ДЕФЕКТ-1: параллельные append теряют записи и врут про успех`

Последовательность `load → push → write → rename` не атомарна как целое. Каждый вызов читает
файл целиком и перезаписывает его; последний `rename` затирает работу остальных.

Измерено:

| Сценарий | Отчитались об успехе | Реально в файле |
| --- | --- | --- |
| 20 параллельных `append` в одном процессе | 11 | 1 |
| 10 одновременных запусков CLI на один файл | 9 | 7 |

Потеря записей в README уже описана как ограничение. Не описано главное: `append()` возвращает
`true`, а `run()` отдаёт `memorySaved: true` на данных, которых в файле нет. Вызывающий получает
подтверждение успеха на потерянной записи — это хуже самой потери, потому что скрывает её.

**Готово, когда:** запись сериализована между процессами (lock-файл через `open(path + '.lock', 'wx')`
с ограниченным числом повторов, backoff и снятием устаревшего лока по `mtime`; чтение файла —
под локом), и `append()` возвращает `true` только если запись действительно попала в итоговый файл.

**Если времени мало:** минимальный честный фикс — перестать возвращать `true` без проверки. Это
снимает худшую часть дефекта за несколько строк. Потеря записей останется, но станет видимой.

### A2. Одна незнакомая запись уничтожает всю историю

**Файл:** `src/memory.js:8-20` (`validateMemory`)
**Тест:** `ДЕФЕКТ-2: одна несовместимая запись уничтожает всю историю`

Валидация работает по принципу «всё или ничего»: любая запись, не прошедшая проверку, отправляет
в карантин весь файл. Проверено: 5 валидных записей плюс одна с `source: "cache"` (значение из
гипотетической будущей версии) — в файле осталась 1 запись, переписка пользователя стёрта.

Это мина замедленного действия на совместимость. Достаточно расширить формат — добавить новый
`source`, новое поле результата — и каждый старый клиент при первом же запуске уничтожит историю.

**Готово, когда:** невалидные записи отбрасываются поштучно, валидные сохраняются. В карантин
файл уходит, только если повреждён сам конверт (`version` не равен 1, `entries` не массив).
Неизвестное значение `source` не должно считаться порчей.

### A3. Объём ответа ничем не ограничен

**Файл:** `src/openai-client.js:38` (`await response.json()`)
**Тест:** `ДЕФЕКТ-7: объём ответа ничем не ограничен (AGENTS.md требует лимит)`

`AGENTS.md`, строка 13, требует от этого модуля «ограничение времени и объёма ответа».
Ограничение времени реализовано и работает корректно. Ограничения объёма нет.

`response.json()` буферизует тело целиком. Измерено: тело 200 МБ увеличило RSS процесса
на 826 МБ — примерно четырёхкратное усиление на буфере, строке и разборе JSON.

Почему это серьёзнее, чем кажется: достаточно большой ответ убивает процесс по OOM, а OOM
**не перехватывается** `try/catch`. Штатная деградация на правила не сработает — процесс просто
умрёт, потеряв и готовый ответ, и запись в память. Весь контур fallback обходится стороной.

**Готово, когда:** тело читается потоком со счётчиком байт и обрывается при превышении лимита,
вынесенного в опцию конструктора. Ориентир — 1 МБ: при `max_output_tokens: 512` реальный ответ
на два порядка меньше, запас огромный.

## Блок B. Высокий приоритет

### B1. Ошибка проводки неотличима от штатного fallback

**Файл:** `src/app.js:8-17`
**Тест:** `ДЕФЕКТ-9: ошибка проводки неотличима от штатного fallback`

`catch` вокруг `client.generate` ловит вообще всё. В результате четыре разных ситуации дают
байт в байт одинаковый результат:

- модель вернула мусор вместо JSON — настоящий fallback, всё правильно;
- `client` не передан вообще;
- у `client` нет метода `generate`;
- внутри `generate` выброшен `TypeError` — то есть баг в коде.

Три последних — ошибки программиста, которые никогда не дадут полезного ответа. Приложение
с разорванной проводкой выглядит полностью исправным и навсегда отвечает демонстрационными
правилами. В логах — штатная причина `invalid_output_or_client_error`, повода искать проблему нет.

**Готово, когда:** `run()` проверяет зависимость на входе
(`typeof client?.generate !== 'function'` — ошибка, а не fallback), а исключения, не являющиеся
`LLMError`, получают отдельную причину вместо общей с мусорным ответом модели.

### B2. Сбой памяти уносит уже полученный ответ

**Файл:** `src/app.js:18`
**Тест:** `ДЕФЕКТ-10: падение памяти уносит уже полученный ответ`

`memory.append`, выбросивший исключение, пробивает `run()` наружу: CLI печатает ошибку и
завершается с кодом 1 — при том что ответ модели уже получен и валиден.

Сейчас это не проявляется только потому, что `JsonMemory` защищается изнутри. Но поле
`memorySaved` существует ровно для этого случая, а сценарий на него не опирается. Любая другая
реализация памяти — БД, сеть, очередь — превращает сбой записи в полный отказ.

**Готово, когда:** `run()` сам перехватывает сбой `memory.append` и возвращает готовый ответ
с `memorySaved: false`.

### B3. Пустая переменная окружения роняет приложение

**Файл:** `src/cli.js:11-16`
**Тесты:** `ДЕФЕКТ-12: пустая переменная окружения роняет приложение...`,
`ДЕФЕКТ-13: пустой MEMORY_PATH молча отключает память`

Оператор `??` срабатывает только на `undefined`, а не на пустой строке. Последствия:

- `OPENAI_MODEL=` в `.env` → выход с кодом 1 **даже в режиме `--offline`**, где модель не нужна;
- `OPENAI_TIMEOUT_MS=` → то же самое;
- `MEMORY_PATH=` → память тихо перестаёт писаться, код выхода остаётся 0, единственный след —
  строчка в stderr.

Оставить строку пустой в `.env` — самое естественное действие пользователя. README при этом
документирует значения по умолчанию, которые не применяются.

**Готово, когда:** пустые и состоящие из пробелов значения приводят к значению по умолчанию.
Удобнее всего маленьким хелпером `envOr(name, fallback)` с `trim()`.

## Ключи и доступы

**Нужен ровно один секрет: `OPENAI_API_KEY`.**

Без него приложение не падает, а молча уходит на демонстрационные правила
(`fallbackReason: "missing_api_key"`). Это значит, что **весь путь через LLM сейчас не проверен
на живом API** — структура ответа подтверждена по документации, а не по факту.

Требование к ключу: доступ к модели с поддержкой **Responses API и strict Structured Outputs**.
Клиент отправляет `text.format.type: "json_schema"` со `strict: true`; модель без этой поддержки
вернёт ошибку, и выяснится это только в бою. Значение `OPENAI_MODEL` из `.env.example` —
пример, а не гарантия: доступность моделей зависит от проекта.

Хранение: `.env`, который уже покрыт `.gitignore` — проверено, утечки в git нет. Ключ не попадает
ни в stdout, ни в stderr — проверено отдельным тестом.

**Остальные переменные секретами не являются**, но до исправления B3 не могут быть пустыми:
`OPENAI_MODEL`, `OPENAI_TIMEOUT_MS`, `MEMORY_PATH`.

**Больше ничего не требуется.** Ни базы данных, ни паролей, ни внешних сервисов: проект
самодостаточен, сторонних зависимостей нет, `npm install` не нужен.

## Что работает правильно

Это не пройдено мимо, а проверено и подтверждено. При рефакторинге не сломать — соответствующие
тесты сейчас зелёные.

**Валидация.** Пробить `validator.js` не удалось. Загрязнение прототипа через `__proto__`
отбивается, лишние ключи отклоняются, пустой и состоящий из пробелов `reply` не проходит,
границы длин (10000 символов на вход, 4000 на ответ) соблюдаются, значения вне `enum`
отклоняются, нестроковые типы отсекаются. Схема пригодна для strict-режима: `additionalProperties`
равно `false`, все свойства перечислены в `required`.

**Таймаут на настоящем сокете.** Проверен не моками, а реальным HTTP-сервером. Обрывается и
медленный ответ заголовками, и тело, приходящее по каплям: 118 мс при бюджете 100 мс. Дедлайн
действительно покрывает и запрос, и чтение тела, как заявлено в README.

**Разбор ответа.** Несколько блоков `output_text` корректно склеиваются, посторонние типы блоков
игнорируются, отказ модели распознаётся, незавершённый ответ распознаётся.

**Изоляция инструкции.** Текст пользователя уходит отдельным полем `input` и не склеивается
с `instructions` — подменить контракт вводом не получилось.

**Восстановление памяти.** Повреждённый файл уходит в резервную копию, а не затирается,
содержимое копии совпадает с исходным байт в байт. Временные `.tmp`-файлы не остаются ни при
успехе, ни при провале. Путь, указывающий на каталог, приводит к мягкой деградации, а не к падению.
Лимит истории соблюдается, вытесняются самые старые записи.

**Безопасность вывода.** Ключ не попадает ни в stdout, ни в stderr. Данные идут в stdout,
диагностика — в stderr, stdout остаётся разбираемым JSON.

**Отсутствующий файл памяти** трактуется как пустая история, а не как ошибка.

## Чего QA не проверял

Говорю прямо, чтобы это не выглядело покрытым.

- **Живой вызов OpenAI.** Ключа нет, а `AGENTS.md` запрещает платные вызовы в тестах. Контракт
  с реальным API остаётся непроверенным — см. раздел про ключи.
- **Потеря питания.** Отсутствие `fsync` перед `rename` означает, что «атомарная» замена не даёт
  гарантии сохранности при аварийном отключении. Это уже честно описано в README как ограничение,
  отдельной задачей не ставлю.
- **Linux и CI.** Всё проверено только на Windows 11 и Node 24.11.1. `rename` поверх
  существующего файла на Windows ведёт себя иначе, чем на POSIX, и, вероятно, объясняет разброс
  в межпроцессном тесте A1 (9 заявленных успехов против 7 записей). На Linux цифры могут
  отличаться — дефект от этого никуда не денется.
