## Принятый контракт

Python выполняет загрузку Parquet, валидацию, аналитику и формирует обязательные CSV. Дополнительно выдаёт `graph.json` для импорта в TRACE и единый `api-snapshot.json` для Go. Go загружает снимок один раз, проверяет его и строит индексы. Формулы ролей не дублируются в Go; на GET анализ не запускается.

Идентификаторы в JSON — строки. Денежные суммы дополнительно представлены целыми тиынами `cents`; сверка операций и рёбер выполняется в них. Дата — `YYYY-MM-DD`, без вымышленного времени. Одинаковые операции сохранены. `row_id` — индекс операции в канонически отсортированном экспорте, **не банковский ID и не исходный номер строки Parquet**. Это уточняет предложение handoff и сохраняет инвариантность содержательного результата к перестановке строк.

API и TRACE обслуживаются одним сервером на loopback. Сервер отдаёт только разрешённые файлы фронтенда; корень репозитория и исходные Parquet не раздаются. Импорт локального graph.json остаётся доступен. Для такого импорта UI не запрашивает операции из потенциально другого серверного снимка.

## Согласованность результатов

`api-snapshot.json` публикуется последним атомарной заменой одного файла. Он содержит schema_version, rule_version, snapshot_id, параметры, хеши входов и SHA256 трёх обязательных CSV. При старте Go проверяет соответствие CSV снимку и отвергает смешанный или повреждённый набор. После загрузки сервер обслуживает неизменяемый снимок; обновление требует перезапуска.

`snapshot_id` идентифицирует входы, правила и CSV; время исполнения не участвует. API сообщает ID снимка, фронтенд проверяет его при загрузке операций. Последовательная запись нескольких файлов не является транзакцией всего каталога: при сбое следует повторить расчёт. Работающий сервер продолжает обслуживать свой уже загруженный снимок.

## Объём этой реализации

Реализуется весь MVP API из handoff, подключение TRACE и P0 правил (время/объём транзита, точная центральность, причины peripheral). Циклы, повторы сумм, календарные события, отдельные обзоры компонент/мотивов и событийное основание coordinator остаются следующим этапом P1. Они не объявляются выполненными самим появлением API. LLM в обязательном сценарии отсутствует.
