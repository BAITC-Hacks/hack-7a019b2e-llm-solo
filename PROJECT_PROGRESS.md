# История работы над проектом «Граф денег»

Дата фиксации: 23 сентября 2026 года.

Документ описывает действия, подтверждённые перепиской, выводом команд и просмотром текущих файлов. Для ранее существовавшего кода указано его текущее состояние: авторство и порядок его разработки в этой беседе не установлены. Это отчёт о ходе работы, а не подтверждение готовности к сдаче.

## 1. Определены задача и правила проекта

Проект предназначен для локального анализа финансовой сети: построения направленного графа переводов, назначения объяснимых ролей, выделения кластеров и формирования очереди ручной проверки.

В [AGENTS.md](AGENTS.md) закреплены контракты выходных файлов, ограничения интерпретации данных и правила командной работы. Роли и оценки являются аналитическими гипотезами, а не доказательствами виновности.

Согласован основной сценарий запуска из корня:

```powershell
python starter/starter.py --data data --out out
```

В правилах этой локальной копии назначена ветка `adilet`. В рамках описанной диагностики коммиты, push и объединение веток не выполнялись; текущее состояние удалённого репозитория при подготовке этого документа не проверялось.

## 2. В проекте подготовлены код, данные и документация

На момент осмотра присутствуют:

| Путь | Назначение |
| --- | --- |
| `data/nodes.parquet` | Исходные узлы |
| `data/edges.parquet` | Агрегированные направленные переводы |
| `data/transactions.parquet` | Отдельные транзакции |
| `starter/starter.py` | Аналитический пайплайн |
| `starter/viewer.html` | Шаблон интерфейса графа |
| `starter/requirements.txt` | Зависимости Python |
| `README.md` | Запуск, методика, ограничения и сценарий демо |
| `starter/README.md` | Краткий запуск и ссылка на основную документацию |
| `architecture.svg` | Схема архитектуры в корне проекта |

В текущем коде уже предусмотрена следующая последовательность:

1. `load_data` читает три Parquet-файла и проверяет обязательные колонки.
2. `validate_data` проверяет дубликаты узлов и пар рёбер, суммы рёбер, соответствие агрегатам транзакций и ссылки на существующие узлы.
3. `build_graph` создаёт направленный граф и добавляет узлы, включая изолированные.
4. `calculate_features` рассчитывает признаки для анализа сети.
5. `cluster_graph` выделяет сообщества и формирует таблицу кластеров.
6. `assign_roles` назначает роли, оценки и объяснения; `build_top_list` формирует рейтинг.
7. `run` записывает три CSV, а `make_viewer` собирает HTML из шаблона и рассчитанных данных.

В шаблоне есть отрисовка направлений, окраска по ролям, фильтры роли и кластера, поиск, карточка клиента, масштабирование и перемещение. Эти возможности обнаружены в коде; проверка их работы в браузере в данной беседе не проводилась.

## 3. Исправлена команда запуска для используемой оболочки

Первая ошибка была связана с использованием PowerShell-пути в Git Bash:

```text
bash: ..venvScriptspython.exe: command not found
```

Было объяснено различие записи путей. Для Git Bash предложена команда:

```bash
./.venv/Scripts/python.exe starter/starter.py --data data --out out
```

Для PowerShell используется:

```powershell
.\.venv\Scripts\python.exe starter/starter.py --data data --out out
```

В последующем присланном выводе PowerShell Python уже запускался. Ошибка перешла с поиска исполняемого файла на загрузку библиотеки чтения данных.

## 5. Найдена причина падения чтения Parquet

Пайплайн остановился при загрузке данных: импорт `pyarrow.parquet` завершился ошибкой загрузки DLL с сообщением, что файл заблокирован политикой управления приложениями.

Код попробовал резервный движок `fastparquet`, но тот отсутствовал в окружении. В текущем `requirements.txt` он также не объявлен. Поэтому итоговое сообщение об установке Parquet-движка скрывало более конкретную первоначальную причину.

Уточнено, что успешный `import pyarrow` и результат `pip check` не доказывают возможность загрузки нативного модуля Parquet.

При отдельной попытке агента повторить импорт окружение сообщило об отсутствии базового `Python312\python.exe`. Это наблюдение из среды запуска агента; оно не доказывает удаление Python на компьютере пользователя и не отменяет предыдущую диагностику DLL.

## 6. Блокировка подтверждена журналом Windows

Агент прочитал журналы через PowerShell. В `Microsoft-Windows-CodeIntegrity/Operational` найдены события `3077` и `3033`, в том числе от 23 сентября 2026 года, 15:17:28.

В них указан заблокированный файл:

```text
.venv\Lib\site-packages\pyarrow\parquet.dll
```

Идентификатор политики из события:

```text
0283ac0f-fff1-49ae-ada1-8a933130cad6
```

Пользователь повторил чтение журнала и прислал те же сведения. Таким образом, причина подтверждена не только текстом Python-ошибки, но и журналом Windows.

## 7. Установлено, какая политика применяется

Пользователь уточнил, что компьютер личный. Проверка реестра показала `VerifiedAndReputablePolicyState = 1`. Попытка агента получить список политик через `CiTool.exe` завершилась отказом в доступе.

Пользователь запустил `CiTool.exe -lp` из PowerShell с правами администратора. Сначала был прислан блок `VerifiedAndReputableDesktopEvaluation` с другим ID и выключенным применением. Затем найден нужный блок:

- имя: `VerifiedAndReputableDesktop`;
- ID: `0283ac0f-fff1-49ae-ada1-8a933130cad6`;
- принудительное применение: `true`;
- авторизовано: `true`.

Это подтвердило связь блокировки с действующей политикой Smart App Control.

Была изучена [справка Microsoft](https://support.microsoft.com/en-us/windows/security/threat-malware-protection/smart-app-control-frequently-asked-questions). Обсуждались подписанная сборка библиотеки и отключение Smart App Control через настройки Windows. Позднее рекомендация отключать защиту первым шагом была пересмотрена в пользу решения без изменения защиты.

Агент настройки защиты не менял. Пользователь не подтвердил отключение Smart App Control или успешный импорт `pyarrow.parquet` после изменения настроек.

## 8. Обсуждена альтернатива в виде CSV

Пользователь сообщил о созданных CSV для чтения вместо Parquet. При подготовке этого отчёта в `data/` действительно найдены:

```text
nodes.csv
edges.csv
transactions.csv
```

Объяснено, что CSV могут заменить входные Parquet для расчёта, если содержат те же данные. При таком чтении нативная Parquet-библиотека не нужна.

Отдельно оговорено сохранение точных `gid`, `src`, `dst`, сумм, дат и значений `is_seed`. При чтении CSV идентификаторы нужно явно сохранять строками либо точными целыми. Если Excel уже округлил длинный идентификатор, последующее чтение строкой его не восстановит.

**Текущий статус:** функция `load_data` по-прежнему читает только `.parquet`. Поддержка входных CSV в этой беседе не реализована. Содержимое CSV и его эквивалентность исходным Parquet не проверены. Исходные Parquet остаются на месте.
